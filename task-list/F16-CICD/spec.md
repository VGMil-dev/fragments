# F16-CICD — especificación

## Alcance exacto

Cambios permitidos:

- `.github/workflows/ci.yml`
- `.github/workflows/release-build-candidate.yml`
- `.github/workflows/release.yml`
- `package.json`, `pnpm-lock.yaml`
- `deploy/production/release-agent/test-release-agent-scripts.mjs`
- `deploy/production/release-agent/test-backup-script.mjs` (nuevo)
- `deploy/production/release-agent/fragments-release-agent.py`
- `deploy/production/release-agent/test_release_agent.py`
- `deploy/production/README.md`
- `task-list/TASKS.md`
- `task-list/F16-CICD/{intent.md,spec.md,evidencie.md}`
- `GOAL.md`, `informe-inicial.md`, `F16-CICD-design.md`, `goldfish_review_report.md`

No se permite ampliar la lista sin registrar primero la razón y verificar que no invade una zona reservada.

## Decisiones

1. Mantener intacto el único trigger de release por tag anotada nueva y el entorno de producción protegido.
2. Añadir `yaml@2.9.1` como dependencia directa solo de desarrollo y parsear los tres workflows como YAML 1.2 con rechazo de llaves duplicadas. Validar triggers exactos: CI `pull_request` a `main`; candidato solo `workflow_dispatch` y guardia `github.ref == refs/heads/main`; release solo `push.tags == [v*.*.*]`.
3. Invocar regresión estructural YAML, test de backup y suite Python del agente en CI, build candidato y release antes de atestación/publicación protegida.
4. Probar `backup.mjs` en una carpeta temporal y con una base SQLite sintética etiquetada `F16-CICD`; verificar que no inventa un backup cuando falta el origen, que el snapshot es legible e íntegro, que el SHA-256 anunciado coincide con el archivo y que la retención elimina solo snapshots vencidos con el patrón permitido. Comprobar permisos POSIX en runner Linux.
5. Mantener backup/restore sin acceso a producción: el test no llama Docker, systemd, GitHub ni proveedores externos.
6. Al guardar un registro `deploying`, persistir por `fsync` + `os.replace` tag/SHA/release ID, refs de imágenes objetivo/previas y sus IDs inmutables, volumen SQLite previo y snapshot de servicios vecinos. Fsync también el directorio después de reemplazar el ledger. Ledger ausente/malformado falla cerrado.
7. El poll crea request único con `O_EXCL` para registros que leyó como `deploying`; puede tener una instantánea atrasada. El aplicador siempre re-lee ledger bajo `flock` exclusivo antes de red/Docker: si el request apunta a estado terminal, lo consume como no-op; solo el mismo registro actual `deploying` puede entrar a recovery.
8. Clasificación exhaustiva y fail-closed: solo `socket.gaierror`, `TimeoutError`/`socket.timeout`, `ConnectionError` (incluye reset/refused) y `http.client.RemoteDisconnected` son transporte transitorio, tanto directos como `urllib.error.URLError.reason` de esos tipos; `URLError` con reason string/otro tipo es permanente `unknown_error`. HTTP 408/425/429/5xx son transitorios y se mapean a `http_transient_status` con número en campo `http_status`, sin body. HTTP 403 es transitorio únicamente si hay exactamente un header `X-RateLimit-Remaining` (lookup case-insensitive), tras quitar solo espacio/tab ASCII vale exactamente `0`, código `http_rate_limited`; duplicados/ausente/otro valor son `http_forbidden`; HTTP 429 y otros 408/425/5xx usan `http_transient_status`; no analizar body/mensaje; cualquier otro 403, todo 3xx de API, 401/404/409/otros 4xx y respuesta malformada/excesiva son permanentes. Los requests API JSON deshabilitan redirecciones y no siguen 301/302/303/307/308. Descargas de assets pueden seguir hasta cinco redirects HTTPS por puerto 443 predeterminado, sin userinfo en URL inicial ni destinos, solo a `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, subdominios con límite de etiqueta de `.githubusercontent.com`. Canonicalizar hostname como ASCII lowercase (ASCII uppercase se normaliza antes); exigir DNS LDH: hostname total de 1–253 octetos, cada label de 1–63 caracteres ASCII `[a-z0-9-]`, con carácter alfanumérico al inicio y final, sin labels vacíos ni punto final. Rechazar IP literal, userinfo, Unicode/IDNA y cualquier sintaxis inválida antes de comparar allowlist. Los hosts exactos solo coinciden exactamente; `.githubusercontent.com` requiere al menos un label no vacío anterior al sufijo con límite de label, por lo que el apex no se permite. sin credenciales. HTTP downgrade, puerto no-443, userinfo, host fuera de lista, bucle o salto adicional son `asset_redirect_rejected`. Detectar bucle por URL visitada usando la tupla en memoria `(scheme lowercase, canonical host, effective port, path-or-/, query)`; no incluir fragmento y nunca registrar la URL/query firmada. Para `git fetch` remoto y `gh attestation trusted-root`, `TimeoutExpired` es `command_timeout` y cualquier código no cero es retryable `remote_command_unavailable`; conservan no-terminal/`deploying` y permiten al poll revalidar la misma tag. `OSError` de lanzamiento es permanente `command_failed`. Para Git local, Docker/Compose/systemctl, timeout/código no cero es error permanente `command_timeout`/`command_failed`; errores tras mutación conservan rollback vivo. No parsear stderr. Excepciones/códigos desconocidos son permanentes por defecto. `targetImageIds` se derivan del `.Id` (`sha256:...`) de cada imagen objetivo tras cargar el archivo verificado; `previousImageIds` de `.Image` en containers vivos. Reconciliar solo comparando IDs `.Image` inmutables en ambas muestras; tags/`.Config.Image` no prueban identidad. Asignar causa estable (`transport_error`, `http_transient_status`, `http_rate_limited`, `http_unauthorized`, `http_forbidden`, `http_not_found`, `http_conflict`, `http_unexpected_status`, `asset_redirect_rejected`, `invalid_response`, `command_timeout`, `remote_command_unavailable`, `command_failed`, `provenance_mismatch`, `artifact_invalid`, `unknown_error`); el ledger almacena `error: {code, http_status?}` solo para `rejected`/`recovery_required`, omitiendo `http_status` si no aplica; cada retry emite exactamente JSON `{event:"release_retry", release_id:string, tag:string, code:ErrorCode, http_status?:integer}`, sin campos adicionales ni body/mensaje remoto/stderr/secretos; tests incluyen sentinel strings en body, stderr, excepción y secreto sintético, y comprueban que ninguno aparece en logs o serialización. El objeto ledger error permite solo `{code, http_status?}`. Los transitorios consumen el request sin Docker, no crean terminal antes de despliegue y conservan `deploying` durante recovery para reintento por poll. Permanentes previos al cambio escriben `rejected` con release ID/tag/código de causa; permanente ante `deploying` escribe `recovery_required`. Ambos estados son terminales y no se reintentan.
9. Reconciliar sin Compose bajo `flock`: IDs `.Image` inmutables objetivo exactos + salud API/web/HTTP + volumen/vecinos intactos → `deployed`; IDs `.Image` previos exactos + salud + volumen/vecinos intactos → `reconciled_previous_state`. Releer inmediatamente antes de guardar la transición y requerir que las dos observaciones coincidan. Imagen mixta/desconocida, salud caída, volumen/vecinos distintos, baseline incompleto o inconsistencia → `recovery_required`, cero llamadas Docker mutadoras y runbook manual; fixture específico mantiene `.Config.Image` igual a tag ledger y cambia `.Image` a ID distinto de target/previous con salud/volumen/vecinos sanos, y exige recovery_required con cero mutaciones. Ledger ilegible falla cerrado.
10. `process_release` y `--rollback-latest` usan el mismo `flock` exclusivo. El CLI manual evalúa solo la última entrada del ledger, sin filtrar entradas anteriores; solo muta si esa última está `deployed` o `rollback_failed`, baseline completo, `.Image` actuales idénticos a `targetImageIds`, volumen/vecinos iguales al baseline y health de ambos containers conocida y sana; `deploying`, `recovery_required`, baseline incompleto, imágenes previas/mixtas/desconocidas o health fallida bloquean mutación y requieren intervención. El poll es solo lector y puede crear una solicitud atrasada; el aplicador relee ledger y solo reconcilia el estado todavía `deploying`. `apply_queue` elimina el request en `finally`; si el agente muere antes, el request persistente queda disponible para `path`/siguiente apply. Intervenciones manuales Docker/config requieren detener timer/path, no matar un apply en curso y esperar que `fragments-release-apply.service` quede `inactive`; `--rollback-latest` requiere además los guardrails de estado/IDs/baseline anteriores. El agente no puede excluir a root que ignore el runbook.
11. Para fallos capturados mientras el proceso vive, mantener rollback de imágenes actual. Si una muerte interrumpe el rollback, al siguiente ciclo los dos estados exactos se reconcilian; cualquier otro resultado requiere intervención manual. Nunca restaurar SQLite automáticamente.
12. Esta tarea no cambia `apps/api` ni las migraciones. Una tarea futura que incluya DDL debe verificar el binario anterior contra el esquema migrado o especificar rollout/rollback expand-contract; una prueba que solo clasifique sintaxis SQL no se considera prueba de compatibilidad.
13. Documentar que el rollback automático vuelve a imágenes de código, deja SQLite intacta y que el destino actual de backup sigue en la misma VPS. No afirmar que existe recuperación ante pérdida total del host.

## Criterios de aceptación

- **Actions — integridad:** parsear YAML y dado cualquier workflow/job, cuando un `uses` no tenga SHA completo de 40 caracteres o no sea uno de los pins aprobados, la regresión falla.
- **Actions — activación:** fixtures YAML válidos con `schedule`, trigger adicional, tag filter más ancho o guardia de rama removida deben fallar la política.
- **Actions — aislamiento:** `runs-on` debe ser exactamente uno de `ubuntu-24.04`, `ubuntu-24.04-arm`, `ubuntu-latest`; runner self-hosted, matriz/expresión dinámica u otro valor falla.
- **Actions — privilegios:** permisos globales exactos `contents: read` en los tres workflows; jobs CI/candidato no amplían; en release los mapas exactos son `verify-build={contents:read}`, `attest-package={actions:read,contents:read,attestations:write,id-token:write,artifact-metadata:write}`, `publish-approved-release={actions:read,contents:write}` con environment `fragments-production`. Alteraciones de cualquiera fallan.
- **Backup — éxito sintético:** origen, destino, fixtures de retención y archivos ajenos están dentro de una carpeta temporal; con una fila marcada `F16-CICD`, el snapshot retiene esa fila e `integrity_check=ok`; el test calcula SHA-256 del archivo independientemente y lo compara con la salida; verifica permisos privados en Linux.
- **Backup — fallo seguro:** dado un origen inexistente, el script termina con error y no crea un snapshot vacío.
- **Retención:** origen, destino, snapshots vencidos/recientes y archivo no coincidente viven en la carpeta temporal; solo se elimina el snapshot vencido con nombre permitido.
- **Agente — caída tras cada frontera:** simular interrupción después de fsync/replace del ledger, backup, recreación API, recreación web y durante rollback; reiniciar test harness y verificar el estado exacto resultante.
- **Agente — caída antes/cierre revertido:** si imágenes previas están sanas y volumen/vecinos coinciden, actualiza esa misma entrada a `reconciled_previous_state`, cero Compose y no vuelve a intentar el release.
- **Agente — caída después de aplicar:** si ambas imágenes objetivo están sanas y concuerdan con tag/SHA/volumen/vecinos, actualiza esa entrada a `deployed`, cero Compose.
- **Agente — estado parcial/desconocido:** imagen mixta/desconocida (incluida tag igual con `.Image` distinto), salud fallida, volumen/vecinos diferentes o baseline incompleto marca `recovery_required`, sin Compose ni Docker mutador.
- **Agente — ledger/procedencia:** ledger malformado falla cerrado; fuente GitHub no disponible conserva `deploying` y permite reencolar en siguiente poll; terminal no se reencola; request se consume después de aplicar y se recrea únicamente por poll cuando el estado sigue `deploying`.
- **Idempotencia:** para un `deploying` único de la misma tag/SHA/release ID actualiza el registro existente; registro duplicado, identidad distinta o estado terminal se rechaza sin añadir filas.
- **Clasificación de errores:** probar 408/425/429/5xx, 403 con header Remaining=0, 403 ordinario/body engañoso, 3xx/401/404/409/otros 4xx, respuestas malformadas/excesivas, `URLError` con reason desconocido/string y tipos socket no enumerados (permanentes), API redirect 301/302/303/307/308 sin segunda solicitud; asset URLs/redirects con puerto no-443/userinfo rechazados; hostname DNS uppercase normalizado, probar labels 1/63/64, hostname 253/254 octetos, guiones extremos, label vacío/doble punto, trailing dot, IP/IDNA/lookalike, rechazar apex `githubusercontent.com` y `notgithubusercontent.com`, aceptar `x.githubusercontent.com`; header 403 duplicado o whitespace interno inválido no habilita retry; OWS permitido alrededor del valor se normaliza; redirects de asset permiten hasta cinco saltos solo por HTTPS a hosts allowlist, incluyendo fixture de ciclo A→B→A; rechazan cualquier host `.amazonaws.com`, cross-origin fuera de allowlist y downgrade; TimeoutExpired/código no cero en git fetch y gh trusted-root (retryable), OSError de lanzamiento, fallos locales Git/Docker/systemctl (permanentes), evento JSON release_retry con esquema cerrado exacto, máximo uno por release cada ciclo de poll de cinco minutos sin backoff adicional, sentinels body/stderr/excepción/secreto ausentes, shape cerrado del ledger error y excepción desconocida; solo las categorías transitorias explícitas permiten reintento sin Docker y toda categoría no reconocida falla cerrada. Permanente previo crea `rejected`; durante `deploying` crea `recovery_required`.
- **Request atrasado:** dado que poll crea request desde snapshot viejo mientras apply convierte el registro a terminal, el consumer relee bajo `flock`, borra la solicitud sin bajar assets ni mutar Docker.
- **Serialización:** deploy, rollback y recovery compiten por un lock exclusivo; pruebas paralelas verifican que una segunda operación no ejecuta Compose mientras la primera sostiene el lock. La suite prueba que una entrada antigua `deployed` seguida de `recovery_required`, `deploying` o cualquier terminal no elegible provoca cero operaciones Docker mutadoras; rollback manual rechaza recovery_required y toda discrepancia target ID/volumen/vecinos/health con cero operaciones Docker mutadoras, y solo permite el estado objetivo completo y sano.
- **Migración/rollback:** F16 no modifica migraciones; no se añade un analizador sintáctico que no pruebe binario previo. Una futura migración tiene que superar un test de compatibilidad explícito antes de permitir release con rollback solo de código.
- **Suite agente:** la suite Python corre en los tres workflows y usa mocks/fixtures sintéticos sin red ni Docker.
- **Integración:** las regresiones se ejecutan en los tres workflows antes de pasos que publiquen artefactos de release; el set local no requiere secretos ni red.
- **Producción:** no se crea una tag, release ni despliegue ni se modifica la protección efectiva de GitHub.

## Comandos de verificación previstos

- `node --test deploy/production/release-agent/test-release-agent-scripts.mjs deploy/production/release-agent/test-backup-script.mjs`
- `python3 -m unittest discover -s deploy/production/release-agent -p 'test_*.py'`

## Riesgos y límites conocidos

- Los snapshots locales no cubren pérdida de la VPS. Elegir/configurar almacenamiento externo requiere un destino y política operativa propios y queda fuera de esta tarea.
- Las migraciones 1–10 observadas son aditivas; F16 no modifica el esquema. F16 no prueba compatibilidad de un binario anterior frente a futuras migraciones; esas tareas deben añadir ese test antes de habilitar release/rollback.
- Los códigos no cero remotos de `git fetch`/`gh attestation trusted-root` se reintentan indefinidamente cada cinco minutos; fallos permanentes de configuración pueden dejar el release pendiente hasta que operación detenga timer, path y service (confirmando apply inactivo), corrija la causa y reanude el poll de la misma tag.
- El resultado verde del workflow GitHub no demuestra que el agente pull haya aplicado una release en la VPS.
